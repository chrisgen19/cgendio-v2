# Case study walkthrough: design

## Why

The case study pages read as plain documents, and the hero is a large glyph that says little about the work. Readers are recruiters, agencies and dev clients who may give a portfolio only a few minutes, so they need proof and reasoning quickly.

Christian compared three previews of `/work/access-hire` in the design lab and chose **The Walkthrough**: a browser frame pinned beside the notes moves through real captures of the shipped site, with a selection box tying each note to a spot on the page. It is the only direction of the three that can work for every project.

The preview runs on hard-coded content. This work makes it a real layout of `/work/[slug]`, with its content in the database and editable in the admin.

## Goals

- `/work/[slug]` shows The Walkthrough for any project that has tour data, reading everything from the database.
- Every other project keeps today's layout, unchanged, and switches by itself once it has tour data.
- The admin project form can create and edit a tour, and the decision, our part and the result.
- Access Hire has its tour on every database, whether it is seeded or only runs migrations.

## Non-goals

- Tours for the other five projects. That is content work for later.
- A visual tool for placing selection boxes. Pixel positions stay JSON for now.
- Shipping The Lift or The Fleet.
- Reworking the design. Layout, motion and fallbacks carry over from the preview as they are.

## Anti-goals (failure even if it technically works)

- Sample copy reaching a database or a deployed page. `sampleCopy` in the lab is invented.
- Any visible change to the five projects without tours.
- A published image showing staff names, phone numbers or customer names, even if the frame crops them, because anyone can open the image URL directly.
- A bad tour edit breaking a public page: invalid data must be stopped when saving.

## Decisions made by Christian

1. **Layout rule:** projects without tour data keep the current layout. The Walkthrough shows only on projects with tour data.
2. **Editing:** in the admin project form, with fields for the decision, our part, the result and the tour stops, and the pixel positions as a JSON field for now.
3. **Empty reasoning fields:** hide any of the decision, our part or the result that is empty, and show the section only when at least one has text. This replaces the project's usual `[placeholder]` rule for these three fields only.
4. **Permission:** Access Hire has agreed to its screenshots being shown publicly.

## Data model

Add to `Project` (hand-check the generated SQL; see the Prisma gotcha in `CLAUDE.md`):

| Prisma field | Column | Type | Notes |
| --- | --- | --- | --- |
| `decision` | `decision` | `String?` | The decision |
| `contribution` | `contribution` | `String?` | Our part |
| `outcome` | `outcome` | `String?` | The result |
| `tourStops` | `tour_stops` | `Json @default("[]")` | Ordered array of stops |

One JSON column, not a table: a tour is always read and saved whole with its project, the existing form saves one row, and order is the array order.

A stop, validated by a Zod schema in `src/server/content-schema.ts` and added to `projectDetailSchema`:

```ts
type TourStop = {
  key: string; // stable id, generated by the form
  heading: string;
  note: string; // may be empty on the first stop only (see Opening frame)
  emphasis: string | null; // words of `note` to pick out; must occur in `note`
  selected: string; // label on the selection box
  onScreen: string;
  path: string; // starts with '/'
  alt: string; // alt text for this stop's captures
  captures: {
    desktop: {url: string; width: number; height: number};
    mobile: {url: string; width: number; height: number};
  };
  positions: {desktop: View; mobile: View};
};

type View = {
  y: number;
  startY?: number;
  x?: number;
  zoom?: number;
  box: {x: number; y: number; w: number; h: number};
  labelAt?: 'right' | 'bottom' | 'inside';
};
```

`View` is the type already used by the preview (`walkthrough-stops.ts`). Positions are in the capture's own pixels.

**When a project has a tour:** at least one stop with a non-empty `note`. Export one helper (for example `hasTour(project)`) and use it everywhere the decision is made.

**Opening frame:** what the frame shows before the first note reaches the reading line. If the first stop has an empty `note`, it is used only as the opening frame and gets no note row. Otherwise the first stop is also the opening frame. An empty note anywhere else is a validation error. Access Hire uses this for its "Brand banner" opening.

## Public page

`src/app/work/[slug]/page.tsx` and `src/app/preview/[type]/[slug]/page.tsx` both choose the layout with `hasTour`, so a draft preview matches what publishing will show.

Page order with a tour: header and tour, then the write-up, then the reasoning section if any field has text, then the existing `NextProject` and `ContactCta`. `NextProject` stays in the route, not inside the layout.

- **Header:** as in the preview: All work, Live site, eyebrow, h1, summary, role, stack. Add a Repository link beside Live site when `repoUrl` is set, so a project does not lose it on getting a tour. The Client fact is left out: the title already names the client on this layout.
- **Tour:** as in the preview. `Tour stops` replace the hard-coded `NOTES`, `STOPS` and `screens`.
- **Write-up:** the project's `caseStudy` Markdown through the existing `renderMarkdown`. This replaces the preview's hard-coded "Before the rebuild" block. If `caseStudy` is empty, the section is left out.
- **Reasoning:** the preview's "Why we built it this way" section, with a row for each non-empty field and no section if all are empty. Text is plain, not Markdown.
- **The cover image and glyph** are not shown on this layout. They still drive the home page cards and social images.

**Grouping captures:** the preview's frame keeps one layer per page and pans within it, so two stops on one page scroll rather than slide. Replace `ScreenKey` with a key made from the stop's desktop and mobile URLs. Stops that share both URLs share a layer. Group by that key in first-seen order.

**No live site:** remove the preview's `'accesshire.net'` fallback. With no `liveUrl`, the address bar shows only the path and nothing links out.

**Images:** use `next/image` with the same R2 check as `CoverImage` (`isOptimizableCover`). The first capture is the eager, high-priority one.

**Preserved behaviour:** the IntersectionObserver reading line, the desktop/mobile switch with a View Transition, the sticky compact frame on phones, and the static per-note captures with reduced motion or no JavaScript. Check at 1440px and 390px, light and dark.

## Admin

In `src/components/admin/project-form.tsx`, add a new card:

- **Text fields:** The decision, Our part, The result (multi-line, optional, max 2000 characters each).
- **Tour stops:** a client component holding the list in state, serialised to one hidden `tourStops` input, so the existing `saveProject` flow and `Object.fromEntries` keep working. Add, remove and reorder stops. Reorder with accessible up and down buttons, unless `sortable-list.tsx` fits as it is.
- **Each stop:** Heading, Note, Emphasis, Selected label, On screen, Page path, Alt text, a desktop and a mobile capture upload, and one Positions JSON text area holding `{desktop, mobile}`.
- **Uploads:** extend `UploadField` so it can report the uploaded URL and the image's natural width and height to its parent (read in the browser from the chosen file), without changing its behaviour for current uses. Width and height are stored in `captures`, so nobody types them.
- **Validation:** `projectFormSchema` parses the hidden JSON with the stop schema. Errors are returned as field errors naming the stop and the problem, such as "Stop 3: positions are not valid JSON" or "Stop 3: the desktop capture is missing". Nothing invalid is saved.
- **Saving:** the existing `saveProject` and cache tag apply. `getProjectForEdit` and `ProjectFormValues` gain the new fields.

## Access Hire content

- **Stops:** the eight in `walkthrough-stops.ts` (the opening plus seven notes), with their copy unchanged, including "On screen" lines and emphasis. Positions carry over exactly. The alt text comes from `PAGE_ALTS`.
- **Reasoning fields:** left empty, so the section stays hidden until Christian writes them. None of the sample copy is used.
- **Capture clean-up before uploading:**
  - `home` (both devices): crop the height to end above the blank band of unloaded images and the customer first names. Positions stay valid, because the tour never pans below about 42%.
  - `branches` desktop: paint out the staff names and phone numbers in the image, keeping the image size so positions stay valid. Check the mobile capture too.
  - Check every other capture for names or personal details at full size.
- **Hosting:** upload to the `cgendio-media` R2 bucket, where the covers live, and store the public URLs. Uploaded images are publicly reachable straight away; Christian has agreed to that.
- **Every database:** add the tour to `prisma/seed-data/projects.ts` and backfill it in the same migration that adds the columns, only while empty: `UPDATE ... WHERE slug = 'access-hire' AND tour_stops = '[]'`. A test in the style of `project-brand-migration.test.ts` fails if the seed and the migration disagree, and the seed must write `tourStops`.

## Tests

- **Unit:** the stop schema (opening rule, emphasis must occur in the note, path format, invalid JSON messages), `hasTour`, capture grouping, the form schema, and the migration test above.
- **e2e:** capture URLs are not swapped in `e2e/support/prepare.mts`: the admin form rejects data URLs, so a swap would make every admin save of Access Hire fail. The new spec answers the capture requests itself with `page.route` and the local fixture, so it stays offline. New spec for Access Hire: tour renders, frame changes on scroll, device switch, write-up present, reasoning hidden when empty and shown per field when filled, static fallback under reduced motion. Add a test for saving a tour in the admin, including a rejected bad JSON field.
- **Existing specs that will change:** `e2e/public/case-study.spec.ts` asserts Access Hire's cover image, which the new layout does not show. Point the cover assertion at a project without a tour and keep the rest. Check `a11y.spec.ts`, `reduced-motion.spec.ts` and `placeholders.spec.ts`.
- **Guard for the other five:** an e2e test that a project without a tour still renders the current layout.
- **Quality gate:** as in `CLAUDE.md`. The visual baselines cover home page sections only, so none should change.

## Delivery

The preview ports 3001 to 3003 stop working once the checkout leaves the lab branch.

## Calls I made (for Christian to check)

1. Tour stored as one JSON column on `projects`, not a separate table.
2. A project counts as having a tour when at least one stop has a note.
3. A first stop with an empty note acts as the opening frame only.
4. Extra stop fields beyond those discussed: Emphasis and Alt text, because the design and accessibility need them.
5. The write-up section renders the `caseStudy` Markdown, replacing the preview's "Before the rebuild" block, so no new field is needed. It repeats some of the note text. The "On WordPress" eyebrow and that heading go away.
6. Projects without tours ignore the three reasoning fields, even if filled.
7. Reasoning text is plain, not Markdown.
8. Access Hire's tour is seeded and backfilled by migration, so production has it without manual entry.
9. Captures are cleaned before upload to remove staff and customer details from the image itself.
10. The CSS moves into `globals.css` to follow the project rule.
11. The lab is committed locally on its own branch, never pushed, and stays off this PR.
12. The tour layout keeps a Repository link when one is set, and drops the Client fact.
